## Замечания по приоритету

### R1 — высокий: разные управляющие события теряются как дубли

Места: `bot.py:34`, `bot.py:47`, `migrations/001.sql:9`.

`Store.accept` принимает `message`, `human`, `closed`, `stop`, но ключ уникальности включает только `portal/chat/session/message`. Внутренний контракт не требует отдельного идентификатора управляющего события и не обнаруживает конфликт типов. Поэтому при одинаковом идентификаторе сначала принимается `message`, а последующий `stop` или `human` молча отбрасывается.

Воспроизведено на временной SQLite, без доступа к клиентским данным:

```python
event = dict(portal="demo", chat="1", session="2", message="3", kind="message")
store.accept(event)                  # True
store.accept(dict(event, kind="stop"))   # False
store.accept(dict(event, kind="human"))  # False
store.process_one()
# sessions.state == QUALIFYING, а не DO_NOT_CONTACT / HUMAN_ACTIVE
```

Первопричина: идентичность сообщения используется как идентичность любого события. Это подтверждённый дефект доступного синтетического API, а не утверждение, что такой payload уже получен от реального Bitrix24. Сетевого адаптера пока нет.

Исправление: определить и документировать идентичность для каждого класса событий, отделить дубли от конфликтов и обеспечить доставку управляющих событий. Не ограничиваться механическим добавлением `kind` к ключу без проверки контракта источника. Миграция должна сохранять существующие записи и подавление настоящих дублей. До клиентских отправок добавить регрессии отказа, подключения человека и закрытия.

### R2 — средний: последующие миграции исключаются из Git

Место: `.gitignore:3` и `.gitignore:4`.

Глобальное правило `*.sql` имеет исключение только для `migrations/001.sql`. Новые `migrations/002.sql` и `migrations/003.sql` игнорируются. Если код начнёт требовать такую миграцию, свежий клон или другое устройство останется без неё.

Воспроизведение:

```text
git check-ignore -v migrations/002.sql migrations/003.sql
.gitignore:3:*.sql migrations/002.sql
.gitignore:3:*.sql migrations/003.sql
```

Исправление: разрешить версионируемые SQL-миграции проекта, сохранив запрет на дампы. Проверить новый файл обычным `git add`, без `-f`, и наличие всех миграций в коммите. Не удалять уже применённую `001.sql` и не сбрасывать пользовательскую БД ради изменения схемы.

## Метод проверки

Использован имеющийся переносимый CPython 3.12 из временного каталога, без установки пакетов и без изменения исходников. Его изолированный `python312._pth` не включает корень репозитория, поэтому прямой запуск `-m unittest` первоначально завершился `ModuleNotFoundError: bot`; для воспроизведения тестов явно добавлен корень в `sys.path`:

```sh
python -c "import sys,unittest; sys.path.insert(0,'.'); result=unittest.TextTestRunner(verbosity=2).run(unittest.defaultTestLoader.discover('tests')); sys.exit(not result.wasSuccessful())"
```

Эта особенность переносимого интерпретатора не классифицирована как дефект проекта или падение CI. В README по-прежнему требуется обычный установленный Python 3.12.

Дополнительные сценарии запускались одноразовым кодом с `tempfile.TemporaryDirectory`; тестовые SQLite автоматически удалены. Исходный код в ходе ревью не исправлялся.

## Остаточные риски и непроверенный объём

- Из трёх текущих тестов не следует доказательство восстановления после аварии в середине транзакции, изоляции порталов/сессий, сохранения `stop`/`closed` и корректного HTTP readiness при отказе БД.
- Очередь хранит только идентификаторы и тип события, не текст и нормализованные данные сообщения; это ограничение синтетического этапа, которое необходимо устранить в E3 до подтверждения приёма реальных событий.
- Нет исходящего журнала действий, восстановления неопределённой отправки и актуальной сессии на уровне чата. Эти функции относятся к E3 и не считаются реализованными только по архитектурному описанию.
- Полная проверка установки, аутентификации, коннектора Avito, CRM-полей и очередей невозможна без разрешённой целевой среды. E1 в этой части остаётся открытым.
- Успешный CI проверяет только существующие команды, а не интеграцию с Bitrix24, инженерные расчёты или весь глобальный критерий приёмки.
