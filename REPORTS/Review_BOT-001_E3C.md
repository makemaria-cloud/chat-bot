# Повторное ревью E3C

**Дата:** 20 ноября 2026 года.

**Снимок:** `048df00b8a9c6cd5b5b4230148ab8fa4b16053d2` в `main`.

**Вердикт:** исходные R1/R2 предыдущего ревью исправлены в проверенных сценариях; обнаружена одна оставшаяся ошибка восстановления CRM. E3B пока не принят; нужна узкая доработка E3C, без переработки уже проверенной передачи оператору.

## R3 — средний: обычное следующее сообщение оставляет CRM-обновление без пути восстановления

Места: `outbox.py:153`, `outbox.py:295`, `outbox.py:324`, `outbox.py:386`.

Если после планирования CRM-обновления обрабатывается сообщение с `Plan(reply=...)` или пустым планом без новых CRM-полей, увеличивается версия состояния сессии. Исходящая попытка CRM затем отменяется как `cancelled/local_state_changed`. Данные в `crm_desired` сохраняются, но ссылка `action_id` продолжает указывать на отменённое обновление.

`schedule_crm` рассматривает только проекции с `action_id IS NULL`, `finish` сбрасывает ссылку только для части `crm_create`, а `bind_crm` не освобождает отменённый `crm_update`. Поэтому штатное повторное подтверждение привязки возвращает успех, но синхронизация не возобновляется.

### Воспроизведение

На временной SQLite v5, с тем же порталом/чатом/сессией/ревизией и подтверждённой CRM-привязкой `entity_type=1`, `item=17`:

```text
Сообщение 790 -> Plan(crm_fields={quantity: 2})
Сообщение 791 -> Plan(reply="Synthetic acknowledgement")
Dispatcher обрабатывает очередь

Фактические вызовы транспорта: только message, без crm_update
Очередь сверки: crm_projection / deferred / local_state_changed
bind_crm(projection_id=1, entity_type=1, item=17) -> True
Следующий dispatch_one() -> False
Проекция остаётся deferred / local_state_changed
```

Здесь нет смены владельца, сессии, маршрута, неизвестного результата API или запрета контакта. Это обычный случай: клиент уточнил количество, затем прислал благодарность или иной вопрос без изменения CRM-полей до отправки обновления.

### Что исправить

Разделить устаревшую конкретную попытку и всё ещё актуальную желаемую CRM-проекцию. Для достоверно не отправленного, отменённого по изменению версии обновления обеспечить безопасное перепланирование либо рабочий явный путь восстановления с повторной проверкой состояния и привязки. Не отменять сохранённые проверки `human`, `stop`, закрытия, смены сессии и маршрута. Для `uncertain` никаких слепых повторов не добавлять.

Восстановление не должно требовать от клиента повторно сообщить те же поля или прямой правки SQLite. Оно должно выдерживать рестарт, конкуренцию, повтор команды и действующие уникальные ограничения outbox.

## Что подтверждено

- Все 40 тестов прошли локально на существующем CPython 3.12 с добавлением корня репозитория в `sys.path` для переносимого интерпретатора.
- [GitHub Actions 44791689771](https://github.com/makemaria-cloud/chat-bot/actions/runs/44791689771) через API подтверждён как `completed/success`, `head_sha` соответствует `048df00b8a9c6cd5b5b4230148ab8fa4b16053d2`.
- Новая таблица `crm_desired` сохраняет уточнения отдельно от сетевой попытки; тесты подтверждают применение уточнений после сверки и ожидание отдельной привязки новой сессии.
- Повтор handoff после подтверждённого отказа требует новой просьбы, разрешения оператора и паузы от 60 секунд; конкурирующие разрешения не создают несколько попыток в существующем тесте.
- Для неоднозначного или принятого handoff повтор остаётся запрещённым.
- Тест миграции v4 -> v5 сохраняет существующие действия и восстанавливает проекцию из имеющихся записей.
