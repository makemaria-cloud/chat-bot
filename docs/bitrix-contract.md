# Контракт Bitrix24

## Вход E3A

Входной HTTP-контракт основан на официальном режиме webhook для Bot API 2.0 и типе `ONIMBOTV2MESSAGEADD`. Токен из `auth[application_token]` сравнивается с `custom` и значением зарегистрированного botToken. Портал и ID бота заданы доверенной конфигурацией. Присланные адреса REST не используются. OAuth, другие режимы регистрации и конкретная версия целевого портала требуют отдельной проверки.

Из формы читаются идентификаторы `data[bot][id]`, `data[chat][id]`, `data[message][id]`, `chatId`, `authorId`, признаки `entityType` и `isSystem`, текст и тип события. Доверенная привязка по порталу, чату и **конкретному сообщению** возвращает линию и коннектор, исходную сессию и автора, роль и отдельно актуальную сессию с монотонной версией и владельцем. Производственный источник привязки пока открыт. В частности, текущая сессия из `imopenlines.dialog.get` сама по себе не подтверждает принадлежность запоздалого сообщения. История с `SESSION_ID` может помочь проверить членство сообщения. Роли, переход владения, закрытие, ревизии, формат полей и права нужно подтвердить на портале.

Пример синтетической привязки лежит в `examples/bitrix-context.json`. Синтетическая форма использует бот 456, чат 112, автора 27, сообщение 790 и `entityType=LINES`. Исходный запрос и токен не сохраняются. Хранятся идентификаторы, источник, роль, линия, коннектор и ограниченный текст клиента. Текст оператора отбрасывается. Пока политика хранения целевых данных не согласована, использовать только синтетические тексты.

Обработчик отвечает 200 после транзакции записи или после фильтрации подтверждённого события. 403 означает неподтверждённый источник, бот или маршрут, 409 — конфликт данных, 503 — недоступность локального хранилища либо отсутствие конфигурации. Ограничения на экземпляр сервера: 120 запросов за минуту, тело 32 КиБ, 256 полей, текст 8192 символа, таймаут чтения 5 секунд на операцию. Для сетевого развёртывания потребуются ограничения соединений и общий лимитирующий прокси с HTTPS. Платформа не гарантирует повторную доставку ошибки.

## Исходящие действия E3B

Планировщик получает минимальный контекст и возвращает `Plan` без ввода-вывода. Переход состояния и запись намерения фиксируются вместе. Диспетчер проверяет маршрут, текущую сессию, версии привязки и состояния, владельца и ожидающие управляющие события. При включённом транспорте обязательна свежая проверка внешнего источника сессии, владельца, линии и коннектора. Для CRM она также подтверждает существующую привязку либо разрешённое отсутствие привязки. После внешнего чтения локальная проверка повторяется.

- `planned` и `in_flight` обозначают ожидающее действие и записанную попытку.
- `api_accepted` требует подтверждения результата отправки или передачи. Успешное добавление или обновление CRM с валидным идентификатором подтверждается ответом API.
- `not_sent` применяется при выключенной отправке, отклонении, нехватке прав или лимите. `cancelled` применяется, если состояние изменилось или привязка не подтверждена.
- `uncertain` требует ручной сверки после таймаута, сбоя, неожиданного ответа или прерванной попытки. Автоматический повтор отсутствует. Проверенный результат можно записать через внутренний `Dispatcher.confirm`. Для CRM-создания требуется фактически найденный ID элемента. Без подтверждения отмена записи и повтор не выполняются.

Вызов REST выполняется вне транзакции. Между последней проверкой и фактическим исполнением на стороне Bitrix24 остаётся окно гонки. Принятый API вызов уже нельзя отозвать локальной транзакцией. Для очереди клиентов переход в обработку человеком или неоднозначный handoff обрывает ожидающие ответы. Историю и факт подключения сверяет оператор. API работает с текущей сессией чата по `CHAT_ID`, поэтому проверка принадлежности непосредственно перед вызовом критична.

CRM сначала использует подтверждённую привязку. Создание требует явного разрешения на тип сущности, проверки отсутствия привязки и разрешённых полей. До ручной сверки неопределённое создание блокирует новые автоматические создания по этому чату. Точные маппинги целевого портала ещё открыты.

### Подготовка разрешённой тестовой линии

1. Сверить права доступа к Bot API, открытым линиям, истории сессии и CRM. Зарегистрировать Bot API 2.0 с HTTPS-обработчиком и подключить только отдельно утверждённую тестовую линию. Для эксперимента использовать отдельные тестовые данные.
2. Подтвердить коннектор и поля событий, настроить доверенный источник актуальной сессии и владения, заполнить явный список разрешённых CRM-полей. Пока источник не проверен, использовать локальный синтетический воркер.
3. Для отдельного тестового запуска транспорт `BitrixRest.from_environment` берёт базовый HTTPS-адрес из `BOT_BITRIX_REST_ROOT`, ограничивает его согласованным порталом и не следует перенаправлениям. Диспетчер требует точный тестовый маршрут и проверку привязки. Обычный CLI этот транспорт не включает.
4. При отключении остановить отправитель, снять бота с тестовой линии и отозвать тестовые учётные данные. Сохранить список неоднозначных попыток для сверки. Перед обновлением схемы сделать резервную копию SQLite. Для возврата предыдущего кода использовать совместимую резервную копию.
