# BOT-001: доработка E2A и продолжение E3

**Приоритет:** высокий.

**Основание:** [проверка E1/E2](../REPORTS/Review_BOT-001_E1_E2.md), исходное [глобальное ТЗ](../TASK.md).

**Репозиторий/ветка:** `makemaria-cloud/chat-bot`, `main`.

## Решение по отчёту

E1 принимается в границах локального аудита; проверка целевого портала остаётся открытой. E2 — работающая локальная основа, но до интеграции обязательны исправления R1/R2. Три исходных теста, replay, локальные HTTP-проверки и успешный CI на `431987f` независимо подтверждены.

Не переписывать работающую основу без необходимости. Не начинать E4/E5 вместо исправления надёжности событий. Отсутствие доступа к порталу не мешает E2A и локальной контрактной части E3.

## E2A. Исправления основы

### Обязательный результат

1. Исправить идентичность событий: повтор одного события подавляется, различные управляющие события не теряются при совпадении идентификатора сообщения. Конфликт одного ключа с несовместимыми данными не считать обычным дублем молча.
2. Отразить изменение собственной схемы SQLite новой версионируемой миграцией с сохранением данных. Проверить обновление с базы версии 1 и создание чистой БД. Пока SQLite — единственное хранилище, проверять его реальную схему через PRAGMA; не имитировать PostgreSQL `information_schema`.
3. Исправить `.gitignore`, чтобы все проектные SQL-миграции попадали в Git обычным добавлением, а дампы и локальные БД — нет.
4. Расширить регрессии: разные типы событий с совпадающим message ID, настоящие дубли каждого типа, `stop`, `closed`, человек, изоляция порталов/чатов/сессий, конкурентное принятие и обработка.
5. Проверить восстановление: событие принято и сохранено, процесс остановлен до обработки, новый процесс обрабатывает событие; сбой до фиксации обработки не оставляет промежуточно изменённую сессию и потерянное событие.
6. Добавить автоматические проверки `/health`, `/ready`, неизвестного пути и отказа хранилища. Readiness отражает готовность локального компонента, не заявляет готовность Bitrix24-интеграции, которой пока нет.
7. В CI проверять также повторный replay с ожидаемыми результатами, не только успешный код возврата одного запуска. Сохранять воспроизводимость без внешних сервисов и секретов.

Не использовать случайный новый ID на каждом повторе как обход дедупликации; не сбрасывать БД для прохождения миграционного теста. Запрет общения и остановка после человека должны проверяться повторно на уровне исходящих действий в E3.

### Сдача E2A

- Отчёт `REPORTS/Report_BOT-001_E2A.md`: причины ошибок, исправления, команды и фактические результаты, нерешённые ограничения.
- Актуализированные `PLAN.md`, `README.md` и `docs/architecture.md` при изменении контракта.
- Сохранять исходные отчёты E1/E2 как историю; дописать ссылку на исправления, не удалять сведения о первоначальном объёме.
- Отдельный коммит на русском, например «BOT-001 E2A: исправить идентичность событий и переносимость миграций», затем `git push origin main`.

## E3. Контрактная интеграция Bitrix24

### E3A. Входной адаптер и устойчивый контекст

1. Повторно проверить официальные документы из TASK.md, зафиксировать используемую версию API и синтетические формы payload. Для всех полей, ещё не проверенных на портале, явно отметить это в описании контракта.
2. Реализовать отдельный входной адаптер: аутентификация выбранным поддерживаемым механизмом, allowlist порталов/линий/коннекторов, разбор поддерживаемого формата, типизация и фильтрация системных/собственных сообщений. Не принимать домен и REST URL из события как доверенные.
3. Не требовать реальных секретов для тестов. При отсутствии конфигурации обработчик должен отказывать безопасно, а не переходить к публичному приёму событий любого портала.
4. До подтверждения приёма сохранять минимальные нормализованные данные, необходимые после рестарта: текст, роли, метаданные и источник события в пределах утверждённой политики. Одних идентификаторов и `kind` недостаточно. Не сохранять весь исходный payload бесконтрольно и не публиковать тексты клиентов.
5. Ввести контроль актуальной сессии/владения на уровне чата и версию состояния: запоздалое событие старой сессии не должно возобновлять автоответ; порядок локального поступления не доказывает порядок событий источника.
6. Дать возможность подтвердить вход быстро после устойчивой записи, а обработку продолжать воркером независимо от HTTP-запроса; документировать запуск и восстановление воркера.
7. Установить лимиты тела, типов входных данных и частоты запросов. Журналы не должны содержать URL с ключами, текст диалога и полные персональные данные.

### E3B. Исходящие действия, человек и CRM

1. Реализовать устойчивый outbox для клиентских сообщений, передачи оператору и CRM-действий. Различать запланировано, принято API, подтверждено, не отправлено и неопределённый результат.
2. Не считать timeout безопасным поводом повторить действие. После неопределённого результата сверять подтверждение при поддержке API либо отправлять на ручную проверку; учитывать то же правило для создания CRM-сущности и handoff.
3. Перед действием сверять портал, актуальную сессию, версию состояния, ручное управление и запрет контакта. Отменять устаревшие намерения, включая уже ожидающие в очереди.
4. Обеспечить атомарную смену состояния и запись намерения. Внешний HTTP-вызов не держать под глобальной блокировкой SQLite, блокирующей приём управляющих событий. Продумать границу гонки уже начатой отправки и честно описать остаточные ограничения.
5. Создать интерфейсы адаптеров отправки, передачи и CRM, с fake transport для локальных проверок и реальным транспортом за явным разрешением. Mock-прохождение не называть подключением портала.
6. CRM: сначала использовать подтверждённую существующую привязку; создание новой только по согласованной политике и без дублей. Маппинг реальных полей не выдумывать: до проверки портала синтетический контракт отдельно.
7. Режим по умолчанию не выполняет внешних мутаций вообще: ни сообщений, ни CRM-записей, ни handoff. Отдельно ограничить разрешённую тестовую линию; переключение production не разрешено этой задачей.
8. Секреты через окружение/штатное хранилище, `.env.example` только с пустыми значениями; расходы на LLM и новые платные сервисы не подключать без согласования.

## Обязательные контрактные тесты E3

- Неверный токен, чужая линия/портал/коннектор, неверный тип или слишком большой payload: отказ без внешних действий.
- Системное и собственное сообщение: нет ответного цикла.
- Положительный вход, повтор, конкурентный повтор, перезапуск и факты/текст после перезапуска.
- Сбой между изменением состояния и записью outbox: либо откат обоих, либо оба сохранены, без пропущенного действия.
- Менеджер/`stop`/закрытие поступили до отправки: клиентское намерение отменено; новый воркер его не оживляет.
- Новая сессия и запоздалое событие старой: нет отправки в неверную или неактуальную сессию.
- API принял сообщение, ответ потерян: состояние неопределённости, повторной отправки вслепую нет.
- Недоступность API, ограничение частоты, ошибка прав и неверный формат результата: различимое состояние и безопасное уведомление, без ложного успеха.
- Неопределённый/ошибочный handoff: нет сообщения «менеджер подключён» как подтверждённого факта.
- CRM с существующей привязкой, повтор создания и неопределённый ответ: нет слепого создания нового лида.
- Режим без отправки: fake transport не фиксирует внешних мутаций для всех трёх видов действий.
- Запуск из свежего клона с новой БД и обновление БД E2; всё работает по README и в CI.

## Формат сдачи и продолжение

Для E3A/E3B допустимы отдельные законченные подэтапы. После каждого: обновить PLAN.md, оформить отчёт в REPORTS с фактическими командами/результатами и ограничениями, проверить staged diff, сделать отдельный коммит с сообщением на русском языке и push в GitHub. В ответе сообщить hash, ветку и результат push. Не откладывать push до E7.

Без данных портала формулировать статус «локальная контрактная реализация проверена, подключение портала не проверено»; соответствующий пункт E3 остаётся открытым. Затем можно продолжать независимые E4/E5 по TASK.md, не утверждая, что бот уже отвечает в открытых линиях.

Для интеграционной проверки запросить у владельца только сведения и штатный доступ к разрешённой среде: тип/версию портала, способ установки, тестовую линию и коннектор, действующие автоответы, карту CRM-полей/очередей, код текущей интеграции при наличии. Токены не пересылать в чат, отчёты или GitHub; production-тесты и E7 требуют отдельного разрешения.
