## Принцип работы

Цель бота — не просто получить телефон, а установить полезный контакт, вызвать доверие, квалифицировать задачу и передать менеджеру контекст, повышающий вероятность первой и повторных сделок.

Целевой пользовательский контур интеграции:

```text
Avito -> существующий коннектор -> Bitrix24 Open Lines -> бот -> CRM / менеджер
```

Исследованный контур Avito webhook и таблиц `daya_lead_chat_*` — кандидат для повторного использования после аудита действующего кода, а не основание создавать второго независимого отправителя в Avito.

## Безопасность данных

Репозиторий не должен содержать дампы БД, реальные переписки, имена, телефоны, адреса объектов, внешние идентификаторы клиентов, токены и другие персональные или секретные данные.

## Локальный запуск BOT-001

Требуется Python 3.12. Команды выполняются из корня репозитория.

```sh
python -m unittest discover -s tests -v
python bot.py replay examples/events.jsonl
python bot.py serve --port 8080
```

Первый replay на пустой базе принимает и обрабатывает два события. Повтор на той же базе возвращает нули. Путь к SQLite задаётся через `--db` перед подкомандой или через `BOT_DB`. Локальные `/health` и `/ready` показывают состояние процесса и число необработанных событий.

При запуске CLI применяет версионируемые миграции к указанной базе. Переход с v1 на v2 сохраняет очередь и состояния. Повторное событие идентифицируется по порталу, чату, сессии, типу и стабильному `event_id`. Синтетические события без `event_id` используют `message` в пределах своего типа. Если один ключ указывает на разные сообщения, воспроизведение сообщает об ошибке.

## Локальная проверка входного адаптера Bitrix24

Для синтетического теста задайте `BOT_BITRIX_TOKEN` в окружении HTTP-процесса. Сервер принимает только события, описанные в локальном файле привязок.

```sh
python bot.py --db bot.sqlite3 serve --bitrix-fixture examples/bitrix-context.json
python bot.py --db bot.sqlite3 worker
```

Оба процесса используют один локальный файл SQLite. Worker можно перезапустить с тем же путём. Команда `worker --once` обрабатывает накопившиеся события и завершается. При ошибке записи обработка откатывается, а событие остаётся в очереди.

`POST /bitrix24/events` принимает форму `application/x-www-form-urlencoded`. Без `--bitrix-fixture` ответ — 503. Подключение рабочего портала пока открыто. Допустимые поля, ограничения и источники подтверждения приведены в [контракте](docs/bitrix-contract.md).

## Исходящие действия

Локальный worker обрабатывает события без внешних действий. Контракт очереди проверяется через `python -m unittest discover -s tests -v`. Планировщик бизнес-ответов подключается на E4.

```sh
python bot.py --db bot.sqlite3 outbox-review
```

Команда выводит идентификатор действия, тип, статус и причину для действий, требующих сверки, без текста и CRM-полей. После прерванной попытки она переводит запись старше 60 секунд в неопределённое состояние. Перед включением транспорта требуется профиль разрешённой тестовой линии и проверка источника актуального владения и CRM-привязки. [Контракт и порядок отключения](docs/bitrix-contract.md).

В `outbox-review` также видны отложенные `crm_projection` и `handoff_request`. Локальные команды для оператора:

```sh
python bot.py --db bot.sqlite3 outbox-confirm ACTION_ID --crm-item ITEM_ID
python bot.py --db bot.sqlite3 crm-bind PROJECTION_ID ENTITY_TYPE ITEM_ID
python bot.py --db bot.sqlite3 handoff-retry ACTION_ID
```

Если обычное сообщение изменило версию той же сессии и CRM-обновление было отменено до отправки, повторите `crm-bind` с проверенной привязкой. Команда ставит актуальные поля в очередь на обновление, если маршрут и управление сессией позволяют. Если запись остаётся в `outbox-review` после команды, отправка по-прежнему заблокирована.

Первую команду применяйте после подтверждения созданной карточки в CRM. Вторая записывает отдельно подтверждённую привязку карточки к сессии из отложенной проекции. Третья ставит действие в очередь после новой просьбы клиента и как минимум 60 секунд с момента установленного отказа. При отказе в правах сначала восстановите требуемые права на тестовой линии. Команды меняют локальное состояние и возвращают `{"applied":false}` с кодом 1, если указанный переход недопустим. Внешнее действие проходит отдельные проверки отправителя.
